# Unsigned Local Release Runbook (macOS and Windows)

## Purpose and safety boundary

This is the temporary release path until Quotier Labs has Apple Developer ID and Windows
Authenticode certificates. It creates real versioned release builds locally on the target OS, but
it does **not** make them trusted by Gatekeeper or SmartScreen.

The signed pipeline remains intact at `.github/workflows/release.yml.disabled`. The unsigned scripts
do not call it, do not need its secrets, and write to a different output directory. Do not rename
the workflow to `.yml` until the signing setup in `docs/release-steps.md` is complete.

Unsigned releases are appropriate for limited testers who know the source and verify the published
SHA-256 checksum. They are not a substitute for signing/notarization for broad public distribution.

## What the scripts produce

| Host | Command | Output under `local-release-artifacts/` |
|---|---|---|
| macOS | `./scripts/package-unsigned-macos.sh` | `macos/Quotier Labs[ Beta].app`, unsigned universal `.dmg`, SHA-256 |
| Windows | `./scripts/package-unsigned-windows.sh` from Git Bash | standalone unsigned app `.exe`, per-user unsigned NSIS installer `.exe`, SHA-256 files |

The normal signed scripts continue to use `release-artifacts/`. Neither mode consumes or overwrites
the other mode's artifacts.

## One-time machine setup

### macOS build machine

Install the project toolchain used by the repository: Go, Node/npm, Xcode Command Line Tools, and
Wails CLI v2.15.0. Install frontend dependencies once with `npm ci` in `frontend/`.

```bash
go install github.com/wailsapp/wails/v2/cmd/wails@v2.15.0
```

The script uses Apple's built-in `hdiutil`; it does not require an Apple Developer account or
certificate. A macOS build must be made on macOS.

### Windows build machine

Install Go, Node/npm, Git for Windows (including Git Bash), WebView2 runtime/development
prerequisites required by Wails, Wails CLI v2.15.0, and NSIS with `makensis` on `PATH`. Install
frontend dependencies once with `npm ci` in `frontend/`.

```bash
go install github.com/wailsapp/wails/v2/cmd/wails@v2.15.0
```

Run the script from Git Bash. A Windows installer must be produced on Windows; the macOS script
does not cross-compile it.

## Version and tag rules

Both scripts deliberately fail unless all of these are true:

1. The worktree is clean.
2. `HEAD` has an exact annotated tag.
3. The tag is `vMAJOR.MINOR.PATCH` or `vMAJOR.MINOR.PATCH-beta.N`.

The tag is the single release-version source. A beta tag creates the Beta app identity and data
root; a stable tag creates the production identity and data root. Never retag a different commit or
edit a published release artifact in place.

Example:

```bash
git status --short
git tag -s v1.3.0-beta.2 -m "Quotier Labs v1.3.0-beta.2"
git show v1.3.0-beta.2 --no-patch
```

If GPG tag signing is not configured, `git tag -a ...` satisfies the build guard, but a signed Git
tag provides better source provenance. Do not use a lightweight tag.

## Build procedure

### macOS

On the Mac checkout at the tagged commit:

```bash
git switch --detach v1.3.0-beta.2
./scripts/package-unsigned-macos.sh
shasum -a 256 local-release-artifacts/macos/*.dmg
```

The `.app` directory is useful for local inspection. Distribute the `.dmg`, not a copied bare app
directory, because a directory cannot be uploaded as one GitHub Release asset.

### Windows

On the Windows checkout at the same tagged commit, in Git Bash:

```bash
git switch --detach v1.3.0-beta.2
./scripts/package-unsigned-windows.sh
certutil -hashfile local-release-artifacts/windows/quotier-labs-1.3.0-beta.2-windows-amd64-unsigned-installer.exe SHA256
```

Distribute the `*-unsigned-installer.exe` for normal installation. The standalone `.exe` is for
diagnosis/portable testing and is not the recommended installed experience.

## Verification before sharing

On each native OS:

1. Confirm the filename and Settings version match the exact tag.
2. Test on a clean user account or clean machine/VM.
3. Install, launch, create and save a quotation, export/preview a PDF, quit, and reopen.
4. Install the new version over the prior version while Quotier Labs is closed.
5. Confirm settings, database, managed images, and quotations remain available.
6. Confirm pending database migrations finish successfully on first launch.
7. Uninstall and confirm user data remains available for reinstall unless the user explicitly
   removes it separately.
8. Recompute SHA-256 and compare it with the sidecar generated by the build script.

Do not publish an artifact built from a dirty checkout or one whose checksum changed after build.

## Publish a GitHub Release manually

1. Push the commit and annotated tag: `git push origin HEAD` then
   `git push origin v1.3.0-beta.2`.
2. In GitHub, create a Release for that existing tag. Mark beta tags as **pre-release**.
3. Upload the macOS DMG, Windows installer EXE, and their `.sha256` files.
4. State clearly that the packages are unsigned, name the supported OS/architecture, include the
   checksum values in the notes, and link to this project's source/tag.
5. Document important data migrations and the tested source versions.
6. Publish only after both native clean-machine checks pass.

The in-app release checker only sees published releases. Draft releases are ignored. Beta builds
only see GitHub releases marked pre-release with beta SemVer tags; production builds only see
stable, non-prerelease releases.

## What testers see and how to open the app

Only ask users to bypass an OS warning when they obtained the file from the official Quotier Labs
GitHub Release and verified its SHA-256 checksum.

### macOS Gatekeeper

1. Open the DMG and drag Quotier Labs to Applications.
2. In Finder, Control-click/right-click the app and choose **Open**.
3. Review the warning and choose **Open** again. On newer macOS versions the user may instead need
   System Settings → Privacy & Security → **Open Anyway**, then authenticate.

Do not recommend globally disabling Gatekeeper. Once certificates are available, signed and
notarized releases remove this temporary friction.

### Windows SmartScreen

1. Verify the installer checksum.
2. Open the installer. If Microsoft Defender SmartScreen appears, choose **More info**, verify the
   displayed filename/source, then choose **Run anyway**.
3. Complete the per-user installer.

Do not tell users to disable Defender or SmartScreen globally.

## Manual update behavior

Unsigned tagged builds embed `manual_updates_enabled=true` and no update trust key. When automatic
checks are enabled, the app may query the public GitHub Releases API at most once every 24 hours.
Settings can also check on demand.

For a newer same-channel published release, the app shows **Open GitHub release**. It does not
download an installer, execute a file, or call the signed updater. The user must:

1. Open the official GitHub Release from the app.
2. Download the correct DMG or Windows installer and verify SHA-256.
3. Save work and fully quit Quotier Labs.
4. On Windows, run the newer installer over the existing per-user installation. On macOS, mount the
   newer DMG and replace the old app in Applications.
5. Launch the new version and verify the version in Settings.

Application data is stored outside the installed executable/app bundle, so replacing the installed
application preserves settings, quotations, assets, logs, and backups. On first launch the new app
runs cumulative database migrations before opening the UI. Migrations must remain forward-only and
must be tested from every supported prior release. Back up before any release containing a schema
change; do not expect an older binary to open a database already migrated by a newer version.

## Switching to signed releases later

1. Complete and test all credentials in `docs/release-steps.md`.
2. Rename `.github/workflows/release.yml.disabled` to `.github/workflows/release.yml` and commit it
   before creating the next tag.
3. Build a new version; never replace an existing unsigned GitHub asset with a signed file under the
   same tag/version.
4. Publish the signed DMG/PKG and Windows installer plus signed update metadata.
5. Existing unsigned builds will notify users about that newer GitHub Release. Their final manual
   installation moves them onto the signed build. From then on, the embedded update public key
   enables the verified automatic download/install workflow for subsequent releases.

Do not delete the signed updater or signed packaging scripts. They are deliberately dormant, not
obsolete.
